# 20 - 计算密集型与进程模型

> 对应源码：`src/main/features/utilityProcess.ts` + `src/main/workers/fibonacci.ts` | 演示页：计算性能

## 一、原理：为什么 CPU 密集任务不能放主进程

Electron 的进程模型：

```
主进程 (browser)  ──单线程── 所有 IPC / 窗口事件都走这里
  ├─ 渲染进程 (renderer) × N    每窗口一个，可并行
  ├─ GPU 进程                    图形加速
  └─ utilityProcess × N         你 fork 的 Node.js 子进程
```

**主进程是单线程**：主进程里跑一个 3 秒的 CPU 循环，这 3 秒内所有窗口的 IPC 全部排队 —— 页面按钮点击无响应、窗口拖动卡顿。

## 二、三种计算方案对比

| 方案 | 位置 | 不卡 UI | 不卡主进程 | 适用场景 |
|------|------|:---:|:---:|------|
| 主进程同步执行 | 主进程 | ❌ | ❌ | 只有轻量短任务 |
| **utilityProcess** | 独立 Node.js 子进程 | ✅ | ✅ | 重计算（压缩/加密/图像/解析） |
| **Web Worker** | 渲染进程内线程 | ✅ | ✅ | 页面内的数据处理 |

**utilityProcess 是 Electron 官方推荐的重计算方案**：它拿到完整的 Node.js 能力，且可随时 kill。

## 三、关键代码

```ts
// ── 主进程：fork 子进程 ──
import { utilityProcess } from 'electron'

const child = utilityProcess.fork(join(__dirname, 'workers/fibonacci.js'))
child.on('message', (message) => { /* 收到结果 */ })
child.postMessage({ n: 43 }) // 下发任务
child.kill() // 随时终止

// ── worker 脚本（独立构建入口）──
// process.parentPort 是子进程的通信端口
process.parentPort.on('message', (event) => {
  const { n } = event.data
  const value = fibonacci(n) // 重计算
  process.parentPort.postMessage({ type: 'result', value })
  process.exit(0)
})
```

构建配置（electron.vite.config.ts）—— worker 需要独立入口，否则打包后找不到：

```ts
main: {
  build: {
    rollupOptions: {
      input: {
        index: resolve('src/main/index.ts'),
        'workers/fibonacci': resolve('src/main/workers/fibonacci.ts')
      }
    }
  }
}
```

## 四、复制到新工程的步骤

1. 复制 `features/utilityProcess.ts` + `workers/fibonacci.ts`（替换为自己的计算逻辑）
2. electron.vite.config.ts 的 main 多入口增加 worker
3. `index.ts` 调用 `registerUtilityProcess(getMainWindow)`
4. 渲染进程：

```ts
const res = await window.api.perf.fibInProcess(43) // 启动子进程计算
window.api.perf.onEvent((data) => { /* 结果/终止事件 */ })
await window.api.perf.terminate() // 终止
```

## 五、生产实践建议

- 计算逻辑封装成独立 worker 文件，与主进程代码分离
- 给子进程任务设计超时与错误上报（`child.on('exit')` 监听异常退出）
- 多个任务用队列串行，避免 fork 过多进程
- 轻量 I/O（读小文件）不必用子进程，IPC 开销反而更大
